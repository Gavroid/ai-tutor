# AI-Tutor — план развития по спринтам простым языком

Дата: 2026-08-23  
Проект: `/root/workspace/ai-tutor`  
Цель: довести AI-Tutor до воспроизводимого Math-6 pilot — ограниченного, но надёжного учебного продукта для ребёнка.

## Как читать этот документ

- **Человеко-часы** — чистое время разработки и проверки. Это не календарные дни.
- Оценка дана с учётом уже существующего кода и тестов.
- Время на юридическое решение по лицензиям, предоставление CI-сервера и ручную проверку человеком указано отдельно.
- В план не включены новые школьные предметы до закрытия базового Math-6.
- Production, `.env`, `secrets/` и Nightscout в рамках этого плана не изменяются без отдельного решения и безопасной процедуры.

## Текущая ситуация без технических терминов

У проекта уже есть рабочая основа: страницы, пользователи, темы, объяснения, задания, проверка ответов, прогресс, чат, материалы и автоматические тесты.

Но пока нельзя честно сказать, что ребёнок может стабильно пройти весь путь самостоятельно. Основные причины:

1. Нужно окончательно подтвердить сценарий «выбрал тему → получил объяснение → решил задание → получил разбор ошибки → продолжил обучение».
2. Учебные материалы собраны, но права на их использование ещё не подтверждены.
3. Для части книг качество распознавания текста и страниц не доказано.
4. Система должна сама запрещать показ неподтверждённых материалов.
5. Нужен чистый автоматический запуск проверок перед каждым обновлением.
6. Есть уязвимые старые версии нескольких библиотек; обновлять их нужно по одной, а не всё сразу.

## Главный порядок работ

1. Сначала надёжный учебный сценарий.
2. Затем строгая проверка материалов и источников.
3. Затем автоматические проверки запуска и восстановления.
4. Затем безопасность и обновление библиотек.
5. Только после этого — ограниченный pilot для Math-6.

**Оценка: 4–6 часов разработки.**

### Что сделать

- Зафиксировать, какие файлы уже изменены до начала новых работ.

- Привести статус проекта и git-состояние к одному понятному отчёту.
- Подтвердить, что scope pilot — только математика.
- Отдельно отметить, что ручная проверка ребёнком ещё не выполнена.

### Простыми словами

Создаём «фотографию старта», чтобы позднее не спорить, что было исправлено именно новой работой, а что существовало раньше.

### Результат

Есть один короткий отчёт: что работает, что не работает, какие файлы нельзя затрагивать и какими командами повторяется проверка.

### Проверка готовности

- Базовый regression запускается повторно.
- Нет случайного удаления чужих изменений.
- Зафиксированы ограничения: production не меняется, другие предметы не включаются.

# Спринт 1. Надёжный сценарий объяснения темы

**Оценка: 16–24 часа разработки.**

### Что сделать

- Проверить и закрепить ответ сервера на запрос объяснения темы.
- Разделить понятные для пользователя ситуации: неизвестная тема, нет авторизации, закончился бюджет, временно недоступен AI, ошибка материала.
- Сделать так, чтобы интерфейс показывал человеку понятное сообщение, а не техническую ошибку.
- Сохранить диагностические данные для разработчика: код ошибки и request ID.
- Проверить сценарий на заранее подготовленных математических темах.
- Добавить тесты для успешного ответа и всех основных ошибок.

### Простыми словами

Если ребёнок нажал «Объяснить», система должна либо объяснить тему, либо честно сказать, что произошло и что делать дальше. Нельзя оставлять пустой экран, непонятный код или сообщение вроде «Internal Server Error».

### Результат

Ребёнок всегда получает осмысленный ответ: объяснение, безопасную заглушку или понятное предложение повторить попытку.

### Проверка готовности

- Проходит путь «открыть тему → объяснение → задание».
- Ошибка одного сервиса не ломает весь урок.
- В интерфейсе не показываются JSON, stack trace, внутренние названия полей и скрытые инструкции.

# Спринт 2. Полный учебный цикл Math-6

**Оценка: 20–30 часов разработки.**

### Что сделать

- Проверить 15 приоритетных математических тем.
- Для каждой темы подтвердить наличие объяснения, задания, правильного ответа и разбора ошибки.
- Проверить правильный и неправильный ответ ученика.
- Проверить сохранение прогресса.
- Проверить кнопки «очистить», «начать заново» и повторное открытие темы.
- Проверить чат в рамках конкретной темы.
- Сделать мобильную проверку основных экранов.

### Простыми словами

Не достаточно, чтобы отдельная кнопка работала. Нужно, чтобы ребёнок мог закончить настоящий маленький урок и вернуться к нему позже.

### Результат

Для 15 базовых тем есть единый предсказуемый путь обучения: объяснение, практика, проверка, помощь и прогресс.

### Проверка готовности

- Все 15 тем проходят одинаковые автоматические проверки.
- После обновления страницы прогресс не теряется.
- На телефоне текст и кнопки остаются читаемыми.

# Спринт 3. Защитить качество ответа для ребёнка

**Оценка: 14–20 часов разработки.**

### Что сделать

- Запретить показ внутреннего JSON.
- Запретить служебные ключи, `<think>`, отладочный текст и внутренние fallback-сообщения.
- Привести математические формулы к аккуратному виду.
- Добавить минимальные требования к объяснению: понятный ход решения, шаги и итог.
- Проверить ответы на короткие, сложные и ошибочные запросы.
- Создать локальный набор примеров для повторной проверки без внешнего AI.

### Простыми словами

Даже если AI ответил технически корректно, ответ должен быть пригоден для школьника: без «кухни» системы, обрывков служебного текста и непонятных формул.

### Результат

Есть понятный стандарт качества ответа, который можно автоматически проверять перед выпуском.

### Проверка готовности

- Ни один тестовый ответ не содержит внутренних данных.
- Ответы не выдают правильный ответ без объяснения, когда требуется обучение.
- Набор локальных примеров стабильно проходит проверку.

# Спринт 4. Проверить учебные материалы и права на них

**Оценка: 18–28 часов разработки.**

### Что сделать

- Сверить все 20 записей каталога с реальными файлами.
- Проверить, что файлы не повреждены и имеют правильные контрольные суммы.
- Уточнить источник каждой книги и каждой темы.
- Зафиксировать страницы, с которых взята конкретная тема.
- Разобрать расхождение между 16 фактическими mapping-записями и прежним описанием 15 записей.
- Для каждой записи указать статус: разрешено, требует проверки, заблокировано.
- Не показывать ученику материал, если источник или страница не подтверждены.

### Простыми словами

Нужно точно знать, откуда взялось объяснение, можно ли использовать книгу и на какой странице находится исходный материал. Если это неизвестно — система должна спрятать материал, а не показывать его «на авось».

### Результат

Есть проверенный список разрешённых материалов и отдельный список того, что пока нельзя использовать.

### Внешняя зависимость

Юридическое решение по лицензиям принимает человек. Разработка может подготовить таблицу и проверки, но не может сама выдать разрешение на использование книги.

### Проверка готовности

- У каждой разрешённой темы есть источник, страницы и связь с материалом.
- Повреждённые, неясные и неподтверждённые материалы автоматически блокируются.
- Цитаты не показываются без точной ссылки на источник.

# Спринт 5. Сделать автоматический контроль готовности

**Оценка: 16–24 часа разработки.**

### Что сделать

- Сделать единый автоматический отчёт по готовности каждой темы.
- Запретить противоречия вроде «материал заблокирован, но одновременно показан ученику».
- Сделать итоговые флаги готовности вычисляемыми из проверок, а не редактируемыми вручную.
- Проверять наличие объяснения, задания, источника и допустимого статуса материала.
- Добавить понятные причины блокировки.
- Проверить, что новые записи не обходят правила.

### Простыми словами

Система сама должна решать: можно ли показывать тему. Нельзя поставить зелёную галочку вручную, если книга не проверена или задание отсутствует.

### Результат

Для каждой темы виден честный статус: готова, требует доработки или заблокирована — с объяснением причины.

### Проверка готовности

- Ни одна заблокированная тема не попадает ученику.
- Любое нарушение правил останавливает выпуск.
- Отчёт можно повторить одной командой и получить тот же результат.

# Спринт 6. Подготовить автоматический запуск и восстановление

**Оценка: 24–36 часов разработки.**

### Что сделать

- Подготовить отдельную тестовую среду, не связанную с рабочими данными.
- Проверить запуск проекта с чистой базой данных.
- Проверить повторный запуск обновлений без повторного повреждения данных.
- Проверить адреса здоровья системы и готовности к работе.
- Проверить вход пользователя, Redis, базу данных и учебный сценарий.
- Проверить резервную копию и восстановление.
- Проверить безопасный откат неудачного обновления.
- Сохранять отчёты, скриншоты и логи автоматических проверок.

### Простыми словами

Перед обновлением проекта нужно сначала научиться безопасно проверять его в отдельной копии. Если обновление не удалось, должна быть понятная возможность вернуться назад.

### Внешняя зависимость

На текущей машине нет Docker. Для полноценной проверки потребуется CI runner или отдельный тестовый сервер.

### Результат

Есть воспроизводимая процедура: собрать копию проекта, проверить её, сохранить доказательства и безопасно откатить неудачную версию.

### Проверка готовности

- Проверка запускается автоматически.
- Неудача останавливает выпуск.
- Рабочие данные не изменяются во время теста.
- Backup/restore подтверждены фактическим прогоном.

### Результат

Система использует проверенные версии библиотек, а обновления можно повторять без ручного поиска поломок.

### Проверка готовности

- Проверка безопасности показывает закрытые уязвимости или документированные исключения.
- Основные тесты проходят после каждого обновления.
- Не выполняется автоматическое обновление major-версий без отдельной проверки.

# Критерий готовности простыми словами

Проект можно считать готовым к ограниченному запуску, когда ребёнок может:

1. войти в систему;
2. выбрать разрешённую тему;
3. получить понятное объяснение;
4. решить задание;
5. увидеть разбор ошибки;
6. продолжить обучение;
7. вернуться позже и увидеть свой прогресс;
8. не столкнуться с неподтверждённой книгой, служебным текстом или непонятной технической ошибкой.

До этого момента статус проекта: **внутренняя проверка / кандидат на ограниченный pilot**, а не готовый массовый продукт.
